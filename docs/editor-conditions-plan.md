# 計畫:用基準原本的提示,我們的編輯者還會不會靠內部層得分(2026-11-15,第 2 版)

第 1 版(「模型還是生成條件」的四格設計)被三路冷審否決,理由與修改見 §7。這一版把問題縮小到資料撐得起的範圍。

## 1. 問題
先前三個 factual_update 回合裡,claude-fable-5-2 三次都靠修改內部層的 MLP 得到 0.667。但當時的編輯者是在程式代理環境裡的子代理:
有顧問工具、有我整理的指示、有專案的工作說明。

**要回答的問題:把這些都拿掉,只給基準原本的提示與四個工具,這個模型還會不會做出「可歸因於內部層」的得分修改?**

次要問題(有餘額才做):把輸出上限壓到基準的 4,096、effort 降到 low 之後還會不會。

這一版**不**回答「公布的編輯者為什麼只改詞向量」。已知的相關事實:
- 公布的 gpt-6.1-sol 在這三題的 9 個回合(reasoning low / medium / high)全部有分(8 個 0.667、1 個 0.299),寫入全部落在詞向量矩陣。
- sol-high 每次呼叫平均只輸出 313 token(low 111、medium 161),離 4,096 的上限很遠:Sol 不是被回應上限卡住。
- 公布的 gpt-5.6-terra 在基準條件下曾經有意改寫第 33 層的一個神經元(factual_update seed 0),只是沒有效果。所以「基準條件下不會去試內部層」本來就不成立;罕見的是成功,不是嘗試。

## 2. 條件
服務端:`analysis/iwi_rpc_server.py`(IWIBench 的 Service,MPS)。題目:factual_update seed 2、0、3。
編輯者端:新的驅動程式直接呼叫供應商 API,沒有顧問、沒有其他工具、沒有 system prompt。

| 階段 | 條件 | 回合 | 預估花費 | 進入下一階段的條件 |
|---|---|---|---|---|
| 0a | 找公布的 Sol 回合的原始對話紀錄(若公開):看每次回應的結束原因與最大輸出 | 0 | 0 | 只影響要不要做階段 4 |
| 0b | 驅動程式的離線測試(見 §4)與實際第一個請求的 token 數 | 0 | 0 | 必須通過才花錢 |
| 1 | gpt-6.1-sol,公布的 low 設定(Responses API、不送 temperature、reasoning low、上限 4,096),3 題各 1 次 | 3 | 約 1(快取失效約 7) | 見 §5 的檢查;這是連線、快取與行為的煙霧測試,不是忠實度的證明 |
| 2 | claude-fable-5-2,effort high、max_tokens 32,000,3 題各 1 次 | 3 | 24–38 | **主要的一格。** |
| 3 | claude-fable-5-2,effort low、max_tokens 4,096,3 題各 1 次 | 3 | 14–24 | 只有階段 2 至少 2/3 是類別 A(見 §3)而且餘額夠才做 |
| 4 | gpt-6.1-sol,reasoning high、上限 32,000 | 3 | 2–5 | 只有 0a 顯示公布的 Sol 回合有撞到上限才做 |

claude-fable-5-2 的 thinking 關不掉、不接受 temperature(API 文件;階段 0b 用最小的呼叫確認),所以它沒有「基準的 reasoning none」這一格;
階段 3 是「永遠開著的 thinking 被擠進 4,096」,要當成截斷條件來讀。

## 3. 每個回合的分類(看資料之前定義)
依「服務端的寫入紀錄」加「拆解後各半的分數」(`iwibench_patch_split.py` + `iwibench_patch_eval.py`):

- **A 內部層得分**:只留內部層那一半時目標題答對數 > 0,且只留詞向量那一半時 = base。
- **B 詞向量得分**:只留詞向量那一半時答對數 > 0,且只留內部層那一半(若有)時 = base。
- **C 兩半都需要**:完整 patch 有分,但兩半單獨都低於完整 patch。
- **D 有內部層寫入但沒有內部層得分**:寫入紀錄裡有對內部層張量的成功寫入(不論最後是否還原),但不屬於 A / C。另記它是「有意的修改」還是「當暫存用」(看寫入的運算式是否引用 inspect 的結果或答案 token 的詞向量)。
- **E 沒有分數**:完整 patch 目標題答對數 = base。
- **X 不算結果**:最後一則回應因 max_tokens 被截斷、拒答(stop_reason refusal)、達到花費上限而中止、服務端執行失敗。這些單獨列出,**不計入**「選擇不改內部層」。
- 另外每回合記:輪數、工具呼叫數、是否因 64 輪 / 128 次而結束、每次回應的 stop_reason、輸出 token 總量與單次最大值、服務重啟次數。

## 4. 驅動程式必須符合的(出處是基準的原始碼)
1. 單一則 user 訊息:固定的一句話、空一行、`json.dumps(public, ensure_ascii=False, separators=(",",":"))`,鍵的順序 objective、practice、manifest、token_ids、limits;manifest 要含完整的張量清單(`taskset.py` setup)。由 create 的原始回傳組,不用 `data/iwi-rpc/public.json`。
2. 四個工具,名稱不加前綴,說明用原始碼的 docstring,參數是單一個 `request`,schema 由原始碼裡的 pydantic 類別產生(`taskset.py`)。
3. 呼叫前用同一組 pydantic 類別驗證(嚴格型別、不允許多餘欄位);不合格的呼叫不送到服務、但計入編輯者端的 128 次;合格的以 `model_dump(mode="json", exclude_none=True)` 送出。
4. 工具結果是整個 `{result, counters, revision}`。
5. 錯誤文字:ValueError / KeyError / TypeError(含子類別)→ `Invalid tool request: <訊息前 512 字>`;其他例外 → `GPU service returned HTTP 500`,回合作廢(`client.py`、`service.py`)。
6. 停止:64 輪,或助手訊息裡的工具呼叫累計 128 次,或一則不含工具呼叫的回應(含被截斷的)——回合結束、提交並評目前的 patch,不續問(`taskset.py` editor_limit / finalize;`RESULTS.md`)。
7. Sol:Responses API、`store: false`、`include: ["reasoning.encrypted_content"]`、`reasoning.effort`、`max_output_tokens`、不送 temperature、每輪原樣重放先前的輸出項目(含 reasoning);被截斷且含工具呼叫的回應視為傳輸失敗,該回合記為 X(`editor_proxy.py`)。
8. Fable:不送 temperature 與 thinking 設定,明確設 effort;thinking 區塊原樣回傳、歷史只增不改;同一輪的工具結果放在同一則 user 訊息;不啟用任何會換模型的備援;每次記 stop_reason。
9. 無法從本機原始碼確定、只能照最直接的做法並在結果裡註明的:工具結果與錯誤給模型時的確切排版、schema 的包裝細節、平行工具呼叫的執行順序(這裡依序執行)、達到上限那一輪的工具呼叫是否執行(這裡不執行)、null harness 是否加 system prompt(這裡不加)。若公布的原始對話紀錄拿得到,就用它逐位元比對驅動程式送出的請求。
10. 服務重啟:由驅動程式在輪與輪之間、接近 30 分鐘上限前主動關閉並接回;接回後先核對 revision 與計數器與關閉前相同;把重新發出的 handle 以「舊 ID → 新 ID」的對照表改寫之後的請求(含巢狀運算式);由 handle 衍生的 handle 由驅動程式自己重做。
    離線測試:同一段含 handle 讀取、衍生 handle、add 寫入的工具序列,不中斷跑一次、在每個位置中斷各跑一次,編輯者看到的內容(handle ID 正規化後)與最終 patch 的雜湊必須相同。

## 5. 事先寫下的讀法
- **階段 1(Sol 煙霧測試)**預期:3 個回合都有分、寫入只落在詞向量、每回合 10–30 次工具呼叫、沒有被截斷的回應、快取命中率 > 50%。
  有任何一個回合出現內部層得分(A)→ 那是發現,先停下來檢查。0–1 個有分 → 驅動程式或 MPS 改變了行為,先停。
  這一步通過只表示「連線、快取與大致的行為正常」;3 個回合不足以證明與基準逐項相同。
- **階段 2(主要)**:
  - 3 個回合中 ≥ 2 個是 A → 先前的結果不依賴顧問、我整理的指示或代理環境;這個模型在基準的提示與工具下會做出靠內部層得分的修改。
  - 0 個 A 且 ≥ 2 個是 B → 先前的結果依賴被拿掉的那些東西之一(分不出是哪一個);要照實寫成「拿掉之後它也改詞向量」。
  - 0 個 A、多數是 D 或 E → 它仍然去試內部層但做不成;同樣表示先前的成功依賴被拿掉的東西,或依賴更大的輸出空間(先前單次回應最長 4.4 萬,這裡上限 3.2 萬)。
  - 1 個 A → 不下結論,照計數報告。
  - 多數是 X → 沒有結果,檢查原因。
- **階段 3**:只在階段 2 成立時有意義。A 仍然出現 → 不需要大的輸出空間;全部 X(截斷)→ 這一格在這個模型上不可行,不是「需要思考」的證據;B → 被壓縮後改用詞向量。
- 樣本:每格 3 個回合、同一種事實(職位 → 人名)、分數上限對兩種做法都是 2/3。只報計數;「0/3」與真實比率高達約六成並不矛盾,不能讀成「不會」。

## 6. 花費與停損
- 單價在動用前對照兩家的官方價目頁(Fable 的快取讀取價格各來源不一:0.20 或 0.80 美元 / 百萬 token)。
- 總上限 60 美元。帳本 `data/api-runs/ledger.jsonl` 記每次呼叫的 usage 與金額;**每次送出前先預留這一次的最壞金額**(目前上下文全數以未命中快取計價 + 輸出上限),預留後會超過總上限就不送。
- 每回合的上限:階段 1 每回合 3 美元;階段 2 第一個回合 15 美元,之後依第一個回合的實測調整;達到上限的回合記為 X(被截尾),不當成「沒有改內部層」。
- 開始某個階段前,剩餘預算必須夠付該階段的預估上限,否則不開始。
- Fable 的快取用 1 小時的存活時間,避免長時間生成或服務重啟後整段重寫。
- 階段 2 第一個回合結束後,先回報實測花費再繼續。

## 7. 第 1 版被否決的原因(三路冷審,互不知道彼此;標 ✔ 的我對過來源)
- ✔ S-wide 幾乎測不到東西:sol-high 每次呼叫平均輸出 313 token,4,096 的上限對 Sol 不是限制。
- F-base 照寫的規格送不出去:claude-fable-5-2 不接受 temperature、thinking 關不掉(API 文件;尚未用實際呼叫確認)。
- ✔ S-base 把公布的設定寫錯:公布的 Sol 不送 temperature、走 Responses API 並重放 reasoning。
- ✔ 重現閘門太鬆:公布的 Sol 在這三題 9/9 有分。
- 「改了內部層」沒有可操作的定義;多種結果沒有讀法;F-wide 只有 1 個回合卻是唯一真正未知的一格。
- 花費低估:Fable 先前的回合用了 40–121 次工具呼叫並讀進大量數值,每回合約 4.5–12.5 美元,不是 1.8。
- 服務重啟不是不可見的:接回後 handle ID 會變;在寫入已生效但回覆未送出時被中斷,重送會重複套用 add / scale。
- 跨家族的審查另外指出:兩個模型的「推理」不是同一種機制,跨模型比較會把模型與條件混在一起。

## 8. 已知的限制
- MPS 不是 CUDA。驅動程式不是基準用的框架,§4 第 9 點列的細節無法確認。
- 本機的 IWIBench 原始碼版本(db9475f)與公布回合引用的版本不同。
- 一種事實類型、三題、每格三個回合;分數對兩種做法的上限相同,無法用分數分辨好壞。
- 即使階段 2 成立,也只說明這個模型在這個提示下的行為,不說明其他模型做不到的原因。
