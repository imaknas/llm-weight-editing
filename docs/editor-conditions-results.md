# 結果:用基準原本的提示與工具,兩個編輯者各改了哪裡(2026-11-15)

計畫見 `docs/editor-conditions-plan.md`(第 2 版)。這份文件記錄階段 0–2 的結果;階段 3、4 沒有做(階段 4 依計畫取消;階段 3 留待之後決定)。
本文件在獨立複核之前寫成;複核的結果記在最後一節。

## 條件
- 服務端:`analysis/iwi_rpc_server.py`,直接使用 IWIBench 的 Service(工具、額度、題目、patch、評分),裝置 MPS。
- 編輯者端:`analysis/iwi_editor_api.py` 直接呼叫供應商 API。單一則 user 訊息、沒有 system prompt、四個工具、沒有其他工具。
- 題目:factual_update seed 2、0、3,每格每題 1 次。

| | gpt-6.1-sol | claude-fable-5-2 |
|---|---|---|
| API | Responses(不存檔、逐輪重放加密的 reasoning 項目) | Messages(串流、1 小時提示快取) |
| 生成設定 | reasoning low、max_output_tokens 4,096、不送 temperature(公布的「6.1-sol (low)」設定) | effort high、max_tokens 32,000;thinking 永遠開著,不能關;不接受 temperature |
| 與公布回合的關係 | 同一個模型、同一組設定 | 公布的編輯者裡沒有這個模型 |

兩格的生成設定不同,所以這不是「只差模型」的對照(見「不能說的」)。

## 驅動程式與基準的一致性(階段 0,不花錢)
用原作者公布的原始對話紀錄(Hugging Face 資料集裡 9 個 gpt-6.1-sol 的 factual_update 回合)核對:
- 由服務的 create 結果組出的提示,與公布的 editor-input(seed 2)逐位元相同(182,277 字元);實際第一個請求的輸入 token 數(49,125)與公布紀錄相同。
- 工具定義直接取自公布紀錄(`analysis/iwi_editor_tools.json`)。
- 公布紀錄裡 205 筆未截斷的工具輸出,用我們的排版函式重排後逐位元相同;14 筆被截斷的符合我們實作的規則
  (超過 5,000 token〔位元組數 / 4〕時只留頭尾各 10,000 位元組)。
- 公布的 223 次工具呼叫全部通過我們的參數驗證(基準原始碼裡的 pydantic 類別)。
- 公布的 9 個回合中,沒有任何一次回應撞到 4,096 的上限(單次輸出最大 1,216 token)。
- 服務重啟測試:同一段工具序列,不中斷跑一次、每一步前都重啟(共 8 次)跑一次——編輯者看到的輸出(含 handle ID)完全相同,
  計數器與版本相同,patch 的張量內容逐位元相同。
- 無法核對的:原作者的框架在邊界情況下的行為(達到上限那一輪的工具呼叫是否執行、參數驗證失敗時給模型的確切文字)。
  這六個回合都沒有碰到這些情況(沒有驗證失敗的呼叫,沒有回合因 64 輪或 128 次而結束)。

## 與計畫的偏離
1. **Fable 的 seed 0 與 3 被花費停損截斷後接回。** 我的停損在每次送出前假設整段上下文都沒命中快取,每次預留約 5.4 美元;回合上限 15 美元,
   所以兩題在花到約 9.6 與 10.4 美元(25 與 24 輪、各 76 次工具呼叫)時被擋下。當下驅動程式照流程提交並評了分(兩題都是 0/3),
   那是做到一半的 patch,依計畫歸為 X(被截尾),不是結果。之後修正預留的算法並加上接回功能:編輯者端的對話由完整紀錄重建
   (thinking 區塊原樣),服務端用存檔開新 session。接回時距上一次呼叫約 31 分鐘(seed 0)與 3 分鐘(seed 3)。
   接回後兩題各再做 12 與 11 輪後正常結束。對模型而言可見的差別只有時間間隔。
2. 服務在每個 Fable 回合中重啟 1 次(30 分鐘上限),由驅動程式在輪與輪之間接回。
3. 計畫寫「階段 2 第一個回合結束後先回報實測花費再繼續」:有回報,但當時沒有據此調整回合上限,才造成第 1 點。
4. gpt-6.1-sol 的請求多送了一個 `prompt_cache_key`(基準的轉接程式沒有送);它只影響快取,不進入模型的輸入。

## 能說的
- 在 IWIBench 原本的提示、四個工具與服務端額度下,claude-fable-5-2(effort high、輸出上限 32,000)三題都做出了分數可歸因於內部層的修改;
  同一個服務、同一個驅動程式上,gpt-6.1-sol(公布的 low 設定)三題都只改詞向量,行為與公布的回合一致。
- 先前用子代理跑的三個回合(`docs/patch-ablation-results.md` 的補充一節)有顧問工具、我整理的指示與程式代理環境三個干擾;
  這裡把三者都拿掉,結果的類型相同。所以先前的結果不依賴那三樣東西。
- 兩種做法在這三題上的分數相同(都最多 2/3)。

## 不能說的
- **不能說差別來自模型。** 兩格同時差了模型、推理設定與輸出量(Sol 每回合輸出約 1.3–2.1 千 token,Fable 約 12–16 萬)。
  已知的旁證只有:公布的 Sol 在 reasoning medium / high 下仍只改詞向量,而且它每次回應離 4,096 的上限很遠(不是被上限卡住)。
  Fable 在小輸出量下會怎麼做、Sol 在最高推理強度(xhigh)下會怎麼做,都沒有測。
- **不能說內部層的修改比較好或比較差。** 分數相同,目標題只有 3 題;評分的對照題量不到這類修改的外溢。
- **不是「從權重讀懂運算」。** 三題都靠 inspect_target 取得啟動值來組出修改,而且把 4 次檢查額度用完。
- 範圍:一種事實類型(職位 → 人名)、三題、每格每題一次、MPS;沒有重複,所以不知道同一題重跑的變異。
