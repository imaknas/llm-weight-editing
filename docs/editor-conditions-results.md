# 結果:用基準原本的提示與工具,兩個編輯者各改了哪裡(2026-11-15)

計畫見 `docs/editor-conditions-plan.md`(第 2 版)。這份文件記錄階段 0–2 的結果;階段 3、4 沒有做(階段 4 依計畫取消;階段 3 留待之後決定)。
本文件在獨立複核之前寫成;複核的結果記在最後一節。

## 條件
- 服務端:`analysis/iwi_rpc_server.py`,直接使用 IWIBench 的 Service(工具、額度、題目、patch、評分),裝置 MPS。
- 編輯者端:`analysis/iwi_editor_api.py` 直接呼叫供應商 API。單一則 user 訊息、沒有 system prompt、四個工具、沒有其他工具。
- 題目:factual_update seed 2、0、3,每格每題 1 次。

| | gpt-6.1-sol | claude-fable-5-2 |
|---|---|---|
| API | Responses(不存檔、逐輪重放加密的 reasoning 項目) | Messages(串流、1 小時提示快取) |
| 生成設定 | reasoning low、max_output_tokens 4,096、不送 temperature(公布的「6.1-sol (low)」設定) | effort high、max_tokens 32,000;thinking 永遠開著,不能關;不接受 temperature |
| 與公布回合的關係 | 同一個模型、同一組設定 | 公布的編輯者裡沒有這個模型 |

兩格的生成設定不同,所以這不是「只差模型」的對照(見「不能說的」)。

## 驅動程式與基準的一致性(階段 0,不花錢)
用原作者公布的原始對話紀錄(Hugging Face 資料集裡 9 個 gpt-6.1-sol 的 factual_update 回合)核對:
- 由服務的 create 結果組出的提示,與公布的 editor-input(seed 2)逐位元相同(182,277 字元);實際第一個請求的輸入 token 數(49,125)與公布紀錄相同。
- 工具定義直接取自公布紀錄(`analysis/iwi_editor_tools.json`)。
- 公布紀錄裡 205 筆未截斷的工具輸出,用我們的排版函式重排後逐位元相同;14 筆被截斷的符合我們實作的規則
  (超過 5,000 token〔位元組數 / 4〕時只留頭尾各 10,000 位元組)。
- 公布的 223 次工具呼叫全部通過我們的參數驗證(基準原始碼裡的 pydantic 類別)。
- 公布的 9 個回合中,沒有任何一次回應撞到 4,096 的上限(單次輸出最大 1,216 token)。
- 服務重啟測試:同一段工具序列,不中斷跑一次、每一步前都重啟(共 8 次)跑一次——編輯者看到的輸出(handle ID 正規化後)完全相同,舊的 handle ID 在重啟後仍可使用,
  計數器與版本相同,patch 的張量內容逐位元相同。
- 無法核對的:原作者的框架在邊界情況下的行為(達到上限那一輪的工具呼叫是否執行、參數驗證失敗時給模型的確切文字)。
  這六個回合都沒有碰到這些情況(沒有驗證失敗的呼叫,沒有回合因 64 輪或 128 次而結束)。

## 與計畫的偏離
1. **Fable 的 seed 0 與 3 被花費停損截斷後接回。** 我的停損在每次送出前假設整段上下文都沒命中快取,每次預留約 5.4 美元;回合上限 15 美元,
   所以兩題在花到約 9.6 與 10.4 美元(25 與 24 輪、各 76 次工具呼叫)時被擋下。當下驅動程式照流程提交並評了分(兩題都是 0/3),
   那是做到一半的 patch,依計畫歸為 X(被截尾),不是結果。之後修正預留的算法並加上接回功能:編輯者端的對話由完整紀錄重建
   (thinking 區塊原樣),服務端用存檔開新 session。接回前後兩次模型回應相隔約 31 分鐘(seed 0)與 9 分鐘(seed 3)。接回後兩題各再做 12 與 11 輪後正常結束。
   支持「接回等同於沒有中斷」的證據(找漏洞的複核者查的):截斷都落在一整批工具結果回完之後;接回後第一個工具結果的每個計數器都剛好接續
   (兩題都從第 76 次呼叫、版本 17 / 30 接下去);截斷時提交的 patch 與用來重建的存檔內容相同;服務端的操作紀錄是前一段的延伸;
   接回後第一個請求的快取讀取量等於截斷前最後一個請求的全部輸入(表示重建的對話前綴逐位元相同);截斷當下的分數只寫進紀錄檔,沒有進入對話;
   工具輸出不帶時間,所以模型看不到中斷。無法直接觀察的:最後一輪的重建只有程式碼為憑;接回後記憶體中的權重是由稀疏 patch 重建的。
2. 服務在每個 Fable 回合中於輪與輪之間重啟 1 次(30 分鐘上限);seed 0 與 3 加上接回,各用了三個服務程序。
   六個回合裡,沒有任何一個在重啟或接回之前取得的 handle 在之後被使用,所以「舊 handle 繼續有效」的機制在實際回合中沒有被用到,只有重啟自測為憑。
   計畫寫的是由驅動程式改寫 handle ID,實作改成由服務端讓舊 ID 繼續有效。
3. 計畫寫「階段 2 第一個回合結束後先回報實測花費再繼續」:有回報,但當時沒有據此調整回合上限,才造成第 1 點。
4. gpt-6.1-sol 的請求多送了一個 `prompt_cache_key`(基準的轉接程式沒有送);它只影響快取,不進入模型的輸入。
5. 送給 Anthropic 的請求本體沒有逐次存檔(紀錄裡只有回應與工具結果)。「沒有額外參數、對話只增不改」以程式碼為憑;
   旁證是每一輪的快取讀取量都等於上一個請求的全部輸入減 2,這要求前綴逐位元相同。
   「沒有 system prompt」另外用免費的 count_tokens 驗證過:只用工具定義與 prompt.txt 重建第一個請求,token 數與三個回合第一輪實際的輸入完全相同
   (88,651 / 88,804 / 88,679),所以第一個請求裡沒有其他內容。實際送出的參數:model、max_tokens、output_config.effort、
   tools、messages、stream、頂層的 cache_control(1 小時);工具錯誤帶 `is_error: true`。
6. 驅動程式遇到供應商的暫時性錯誤會重試(最多 6 次,基準不重試);重試沒有記錄,所以無法確認六個回合中有沒有發生過。
7. 截斷規則的門檻(5,000 token)是由公布紀錄夾出來的(未截斷的最大 3,792、被截斷的最小 5,851);Fable seed 0 有一筆 4,485 token 的輸出落在這個區間,我們沒有截斷。

## 能說的
- 在 IWIBench 原本的提示、四個工具與服務端額度下(單次輸出上限放寬到 32,000),claude-fable-5-2(effort high)三題的最終 patch
  都是分數可歸因於內部層的修改——其中一題是不中斷完成的,兩題是被花費上限截斷後接回完成的。
  同一個服務、同一個驅動程式上,gpt-6.1-sol(公布的 low 設定)三題都只改詞向量,寫入位置與公布的回合一致。
- 先前用子代理跑的三個回合(`docs/patch-ablation-results.md` 的補充一節)有顧問工具、我整理的指示與程式代理環境三個干擾;
  這裡把三者都拿掉,結果的類型相同。所以那三樣東西不是必要條件(依據是這三個回合,其中兩個經過接回)。
- 兩種做法在這三題上的上限相同(2/3);Sol 的 seed 2 只有 1/3。

## 不能說的
- **不能說差別來自模型。** 兩格同時差了模型、推理設定與輸出量(Sol 每回合輸出約 1.3–2.1 千 token,Fable 約 12–16 萬)。
  已知的旁證只有:公布的 Sol 在 reasoning medium / high 下仍只改詞向量,而且它每次回應離 4,096 的上限很遠(不是被上限卡住)。
  Fable 在小輸出量下會怎麼做、Sol 在最高推理強度(xhigh)下會怎麼做,都沒有測。
- **不能說內部層的修改比較好或比較差。** 分數相同,目標題只有 3 題;評分的對照題量不到這類修改的外溢。
- **不是「從權重讀懂運算」。** 三題都把 4 次 inspect_target 與 8 次 run_target 的額度用完;從工具呼叫與最後的回覆看,修改是用檢查到的啟動值組出來的
  (推理過程看不到,這一點是推斷)。編輯者確實會去讀特定的權重(例如正規化層的某幾個元素,見複核一節的 seed 3),但那是被啟動值引導的局部查證。
- 範圍:一種事實類型(職位 → 人名)、三題、每格每題一次、MPS;沒有重複,所以不知道同一題重跑的變異。

- 它確認的(「我對過」表示我另外用紀錄查過同一個數字):
  Sol 三題是 B、寫入只有詞向量、分數 0.333 / 0.667 / 0.667;Fable 三題的最終 patch 是 A(拆出的兩半不相交、聯集等於原 patch,
  用基準的 score_episode 重算分數相同);驅動程式送給 Sol 的第一個請求、工具定義、輸出排版、錯誤文字與公布紀錄一致(三題的提示都逐位元相同);

- 它提出、已寫進本文件的:兩題照規則是 X(表格的 ※ 與說明);Fable 這一格超出基準的單次輸出上限(我對過:9 / 11 / 11 次回應超過 4,096);

**盲測重算(同家族子代理)。** 只拿到六個改名為 Q1–Q6 的 patch 檔、題目種子與 IWIBench 原始碼,不准讀本專案的程式、文件、紀錄與輸出,自己寫程式。
- 六個 patch 的分數與上表相同:Sol 0.333 / 0.667 / 0.667,Fable 0.667 × 3;對照題全部保留。每個完整 patch 與 base 各在第二個全新程序重跑,輸出與 logit 完全相同。
- Fable 三題的歸因與上表相同(詞向量那一組對 74 題的輸出 logit 沒有任何影響;內部層那一組重現完整分數),並拆得更細:
  - seed 2:第 31 層的神經元 5007 單獨就重現完整分數;被歸零的 8 個神經元單獨不改變任何輸出字串。
  - seed 0:第 29 層的 4 個神經元單獨重現完整分數;第 27 層的 2 個單獨只做到「Lipman」;沒有任何單一神經元能得分。
  - seed 3:要兩個神經元**加上那一個 layernorm 元素**才成立。少了 layernorm 的修改,兩個神經元會毀掉模型(輸出變成「Mer Mer Mer…」,對照題 5/64)。
    我對過寫入紀錄:編輯者先讀了 `layers.31.pre_feedforward_layernorm.weight` 的第 440–448 個元素(第 20 次呼叫),
    之後兩次把第 443 個元素從 −1 改成 −0.998、再改成 −0.996(第 51、57 次呼叫)。seed 2 的編輯者也讀了第 30、31 層同一張量的第 440–450 個元素,但沒有改它
    (它寫在第 443 欄的權重因此沒有作用:複核者拿掉那兩個數值後,輸出的 logit 完全不變)。
    為什麼這個元素有這個效果,是複核者由原始碼推斷的、沒有量啟動值:Gemma 的 RMSNorm 乘的是 (1 + weight),weight 為 −1 等於把這個殘差通道在進 MLP 前乘以零。
    所以這裡有一個小範圍的「讀權重」:編輯者針對一個特定的元素去讀正規化層的權重,並據此修改。它是由檢查到的啟動值引導的(先看到第 443 維異常大),
    不是從權重本身認出運算;這一句的後半是我依呼叫順序做的推斷,模型的推理內容看不到。

  其他完整 patch 的最小領先:Fable seed 3 2.0、Sol seed 2 3.75、Fable seed 2 4.25、Fable seed 0 6.0、Sol seed 0 7.25。
- 六個 patch 都沒有通過「只回答姓氏」那一題(輸出:Martin、Lip--stein、Friedrich、Markus、Brown、Scholz)。
